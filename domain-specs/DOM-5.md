# [DOM-5] 코스 생성 프로세스

> 💡 **취향으로 후보를 제안하고, 실제 장소와 경로를 확인한 뒤 여행 일정을 완성합니다.**

LLM은 날짜별 후보 제안을 담당하고, 서버는 중복·영업·식사·이동 조건을 검증합니다. 부족한 날짜는 별도로 보충하고 실제 LangGraph 진행 상황을 SSE로 전달합니다.

**구현 기준:** 2026-10-06 · [PR #52](https://github.com/Software-Maestro-GTA/Yeolo-AI/pull/52)·[PR #53](https://github.com/Software-Maestro-GTA/Yeolo-AI/pull/53) dev 병합, [PR #54](https://github.com/Software-Maestro-GTA/Yeolo-AI/pull/54) main 병합 확인(`e848e37`). 실제 서비스 배포·BE/FE 연동 상태는 별도 확인 대상입니다.


## 1. 입력과 결과

`POST /internal/ai/courses`에 내부 인증 헤더 `X-Internal-Api-Key`와 함께 요청합니다.

| 입력 | 역할 |
| :--- | :--- |
| `userId` | 사용자·목적지별 최근 이력을 찾아 반복을 줄입니다. |
| `tasteProfile` | 여행 목적·일정 밀도·장소·활동·음식·계절 선호를 후보 제안에 반영합니다. |
| `mbti` | 취향 프로필이 없을 때 모델의 후보 제안을 돕습니다. 최종 문구에서 MBTI만으로 취향을 단정하지 않습니다. |
| `tripCondition` | 국가·도시, 시작일, 여행 일수, 예산 유형을 지정합니다. 예산 유형은 `cost_effective`·`moderate`·`luxury`입니다. |

취향 프로필과 MBTI 중 하나 이상은 필수입니다. **결과**에는 코스 제목·태그·추천 이유·대표 이미지, 일자별 요약과 방문 장소·도착 시각·체류·예상 비용·다음 이동·방문 팁을 담습니다.


## 2. 전체 생성 흐름

```mermaid
flowchart TD
  A["목적지와 최근 이력 확인"] --> B["날짜별 후보 병렬 제안"]
  B --> C["실제 장소·이동·시간 검증"]
  C --> D["최종 일정·중복 확인·이력 저장"]
  D --> E["추천 문구·사진 보완"]
  E --> F["작업 정리 후 complete"]
  C -. "초기 시도 후 부족한 날짜" .-> R["refill: 최대 2회 보충"]
  R --> C
  R -. "보충 소진" .-> P["repair: 기존 후보 재조합"]
  P --> C
```

흐름도는 주요 경로를 단순화한 것입니다. 검증된 전체 일정은 복구용으로 보관하고, 보충·다양성 개선이 실패하거나 시간이 부족하면 `restore`로 복구해 최종 검사를 거칩니다.

| 단계 | 하는 일 |
| :--- | :--- |
| ① 목적지·이력 확인 · `prepare` | 국가 코드·지역 유형·ID·좌표 범위로 목적지를 확인합니다. 국가별 별칭 예외 목록 대신 공통 기준을 적용하며, 모호한 목적지를 임의로 선택하지 않습니다. 최근 장소·핵심 명소·계획 권역·경험 이력을 읽습니다. |
| ② 날짜별 후보 제안 · `draft` | Gemini가 각 날짜의 가까운 장소와 식사 대안을 제안합니다. 최대 5개 날짜를 동시에 처리하고 각 호출에는 해당 일차와 전체 여행 조건을 전달합니다. 성공한 날짜와 부분 응답은 보존합니다. |
| ③ 실제 장소 확인 · `verify_places` | 장소명·ID·주소·좌표·국가·도시 범위·업종·영업 상태를 확인합니다. 모호한 지점, 폐업 표시, 지역 중심점·역·정류장 등 방문 장소로 부적합한 후보를 제외합니다. 식당과 관광·체험 역할을 구분해 가능한 조합을 만듭니다. |
| ④ 이동·시간 검증 · `verify_routes` | Google Routes의 실제 거리·시간으로 영업시간, 식사 시간, 체류와 다음 도착 시각을 검사합니다. 날짜 간 검증은 병렬화하고, 같은 날짜의 경로는 출발 시각을 계산하며 순서대로 확인합니다. 전체 날짜에서 장소 ID 중복을 배제합니다. |
| ⑤ 최종 일정 구성 · `schedule` | 전체 날짜·장소·이동 구간의 누락과 중복을 다시 확인하고 방문 순서·도착 시각·체류 시간을 확정합니다. 마지막 장소의 다음 이동은 `none`입니다. |
| ⑥ 중복 확인·저장 · `finalize` | 제목·태그·코스 추천 이유를 만들고, SQLite 최신 이력과 원자적으로 중복을 확인해 저장합니다. 제한된 재시도 후에도 반복을 피하기 어려우면 검증된 코스와 상태 안내를 제공합니다. |
| ⑦ 추천 문구 · `enrich_place_copy` | 현재 그래프는 `evidence_only=True`로 실행합니다. 서버가 확인된 장소 유형과 실제 취향 근거로 추천 이유·방문 팁을 작성하며, 이 단계의 추가 LLM 호출은 없습니다. |
| ⑧ 사진 보완 · `enrich_images` | 확정 장소의 실제 사진만 조회하고 확보한 장소 사진을 대표 이미지에 재사용합니다. 사진이 없거나 조회가 지연돼도 완성된 일정은 유지합니다. |

**LLM이 제안하는 정보:** 후보 이름·검색용 영문명·식사 역할·체류 시간·계획용 비용·계획 권역·경험 코드. **Maps로 확인하는 정보:** 공식 장소 ID·위치·주소·유형·영업 상태·정규 영업시간과 실제 조회 경로. 모델의 권역 이름은 공식 행정구역 경계가 아닙니다.


## 3. 일정 기준과 부족한 날짜 보충

| 기준 | 현재 동작 |
| :--- | :--- |
| 정상 방문 수 | 하루 최소 **5곳 = 관광·체험 3곳 + 서로 다른 점심·저녁 2곳**. 식당·카페·베이커리·디저트점은 관광·체험 3곳을 대신하지 않습니다. |
| 일정 밀도 | 느긋함 최대 5곳, 기본 최대 6곳, 촘촘함 최대 7곳을 기존 후보에서 구성합니다. 검증된 5곳이 있으면 6~7곳만을 위해 추가 생성을 강제하지 않습니다. |
| 활동·식사 | 활동 09:00–21:00. 조식 09:00–11:00, 점심 11:30–14:00, 저녁 17:30–20:00. 체류 전체가 해당 범위와 알려진 영업시간에 들어가야 합니다. 점심·저녁은 필수, 조식은 가능한 경우 포함합니다. |
| 이동 | 구간별 실제 이동은 90분 이하이며, 장소 사이에 10분 여유를 더합니다. 이 90분은 구간 이동 기준이고 전체 생성 시간 제한과 다릅니다. |
| 장소·경로 | 확인된 장소와 실제 provider 경로만 채택합니다. 직선거리는 후보 선택·대안 조회 판단에 쓰며 실제 이동 시간·거리로 반환하지 않습니다. |
| 현재 입력의 범위 | 숙소 왕복, 첫날 입국·마지막 날 출국 시각은 반영하지 않습니다. 해당 정보는 아직 요청에 없습니다. |


### 최소 5곳을 먼저 확보합니다

1. 기존 검증 후보에서 정상 5곳 조합을 먼저 찾습니다.
1. 식당이나 관광·체험이 부족하면 해당 날짜에 필요한 대안을 보충합니다. 완성된 다른 날짜와 부분 성공 초안·장소·경로 캐시는 유지합니다.
1. 초기 초안 횟수를 소진해도 **별도 보충 2회**를 수행할 수 있습니다. 취향에 맞는 검증 명소 주변의 실제 장소를 제한적으로 조회합니다.
1. 다른 명소 조합·방문 순서와 유형별 체류 시간을 비교하고 **실제 경로로 다시 검증**합니다. 예를 들어 박물관·미술관 60분, 가까운 공원 45분, 식사 45분을 대안으로 비교합니다. 느긋한 여행 성향과 테마파크·하이킹 같은 긴 활동은 일괄 축소하지 않습니다.
1. 보충과 마지막 정상 일정 재검증을 소진한 뒤에만 **4곳 → 3곳**을 최후 대안으로 사용합니다. 축소 결과에도 별도 점심·저녁과 실제 명소·경로가 필요합니다.
단계별 탐색 횟수와 공통 실행 예산은 제한돼 있습니다. 검증 가능한 조합이 없으면 가짜 장소나 경로로 성공 결과를 만들지 않습니다.

<details><summary>경로와 영업시간 검증의 범위</summary>

- 한국은 대중교통을 우선하고, 해외는 직선거리 1.5km 이하에서 도보를 우선합니다. 경로 실패 시 지원되는 다른 실제 수단을 조회하거나 장소 조합을 바꿉니다. 대중교통 실패의 실제 도보 대안은 직선거리 3km 이내에서 시도합니다.
- 현재 코스 생성 그래프는 수식 기반 도보 추정을 성공 경로로 인정하지 않습니다. 기존 추정 보조 함수가 코드에 남아 있어도 현재 검증 기준은 실제 경로의 양수 거리·시간과 구간 90분 이하입니다.
- 한국 대중교통 요청·캐시에 계획 출발 시각을 반영합니다. 해외는 시간대 자동 판정이 없어 조회 시점 예상치를 사용하며, 여행일 실제 운행을 보증하지 않습니다.
- 정규 영업시간이 제공되면 여행 요일과 전체 체류를 검사합니다. 정보가 없으면 미확인 안내를 유지합니다. 임시휴무·예약 가능 여부까지 확인한 것은 아닙니다.
- 초기 경로 대안 최대 4개, 보충 단계 최대 12개, 마지막 복구 최대 16개를 비교합니다. 모든 후보의 전역 최적 동선을 탐색하는 구현은 아닙니다.

## 4. 시간 제한·오류 복구·SSE

| 항목 | 기본값·상한 |
| :--- | :--- |
| 전체 실행 예산 | 기본 300초. `COURSE_TIMEOUT_SECONDS` 설정을 그대로 적용하고 정리 여유를 남깁니다. 강제 90초·초안 46초 상한은 제거했습니다. |
| 날짜별 LLM 호출 | SDK deadline 60초, 로컬 실행은 공통 남은 시간 이내. 남은 시간이 10초 미만이면 새 호출을 시작하지 않습니다. |
| 초기 생성과 보충 | 초기 초안 단계: 1일 최대 2회, 여러 날 최대 3회. 별도 `refill`: 최대 2회. 날짜별 일시 오류는 한 번 추가 시도할 수 있어 단계 횟수와 실제 LLM 호출 수는 다릅니다. |
| Maps | 개별 HTTP timeout 6초. 병렬 기본 6개·최대 8개. 일시 timeout·네트워크 오류·429·5xx에 한 번 추가 시도합니다. |
| 장소 보충 | 후보 풀 날짜당 최대 30개. 식당: 주변 1km·일차당 1회·검색 최대 10개에서 최대 5곳 채택. 관광 명소: 주변 2km·부족 일차당 1회·최대 5곳. |
| 사진·선택적 개선 | 사진 최대 5초. 이미 완성된 일정의 다양성 개선 작업은 최대 25초와 남은 시간을 따릅니다. 필수 장소 보충은 공통 남은 시간을 사용합니다. |


### 실패한 작업만 복구합니다

- 모델의 일시 timeout·429·5xx·구조화 출력 오류에는 제한적으로 재시도하며 원래 provider 오류 코드를 로그에 남깁니다.
- 한 번의 일시 모델 오류 때문에 부족한 전체 코스를 즉시 확정하지 않습니다. 남은 보충 횟수·시간 안에서 기존 후보를 유지하고 다음 대안을 시도합니다.
- 사진·이력 저장·이동 안내 문구 오류는 이미 검증한 일정을 버리는 이유가 되지 않습니다. 이력 제한이나 축소 같은 이용 관련 상태는 안내합니다.
- 사용자 취소·인증·잘못된 설정은 정상 복구로 숨기지 않습니다. 끝내 유효한 전체 조합을 확보하지 못하면 실패 안내 후 완료 없이 종료합니다.

### 기존 SSE 계약을 유지합니다

- **진행:** 실제 노드 실행 때 `progress`. `step=GENERATING_ROUTE`를 유지하고 `message`에 작업을 설명합니다. 현재는 단계별 코드나 진행률 수치가 없습니다.
- **완료:** 실행 중인 작업·외부 연결을 정리한 뒤 `complete` 한 번, 본문은 `{"course": ...}`입니다.
- **연결 유지:** 이벤트가 15초간 없으면 SSE 주석 heartbeat를 보냅니다. 연결 종료·취소 시 하위 작업도 정리합니다.
- **오류:** 스트림 전 인증·입력·설정 오류는 HTTP 오류, 스트림 후 실패는 안내 `progress`와 함께 `complete` 없이 종료합니다.
**BE의 완료 기준은 HTTP 200이나 progress가 아닌 complete 수신입니다.**


## 5. 추천 문구와 이미지

| 정보 | 작성 방식 |
| :--- | :--- |
| 장소 `reason` | 확인된 유형의 경험과 실제 4~5점 취향을 자연스럽게 연결합니다. 방문 시각·체류 시간·예산을 추천 이유로 반복하지 않습니다. 취향 근거가 없으면 유형에 맞는 경험 가치를 설명합니다. |
| 장소 `memo` | 유형에 맞는 관람·방문 행동 팁을 제공합니다. 확인되지 않은 역사·시설·혼잡·예약·알레르기 안전을 만들어 넣지 않습니다. 기존 영업시간 미확인 안내는 보존합니다. |
| 날짜 `memo` | 최종 장소 유형에서 주요 경험을 골라 짧고 감성적인 1~2문장으로 소개합니다. 조식·숙소 제외나 계산 기준을 반복하지 않고, 축소 일정에는 실제 방문 수를 짧게 안내합니다. |
| 이동 `memo` | 같은 Routes 응답의 탑승·환승·하차·핵심 도보 행동을 한 문단으로 정리합니다. `주요 이동:` 접두사·강제 줄바꿈·총 거리와 시간 반복을 제거합니다. 상세 안내 처리 실패 시 일반 안내로 대체해 실제 경로 수치는 유지합니다. |

> 💡 **현재 장소 추천 이유와 방문 팁은 추가 LLM으로 자유 생성하지 않습니다.**

`course_copy.py`의 LLM 문구 기능은 남아 있지만 실제 그래프는 근거 기반 서버 문구를 선택합니다. 장소별 상세 특징을 충분히 설명하려면 검증 가능한 설명 자료를 확보하는 후속 개선이 필요합니다.

**비용은 계획용 예상치**입니다. 실제 메뉴·입장권 가격이나 총예산 준수를 검증한 값은 아닙니다. 사용자 화면에서는 예상 비용으로 구분하고 같은 가격 주의 문구를 모든 장소에 반복하지 않습니다.


## 6. 반복 방지와 비용 관리


### SQLite는 생성 이력입니다

동일 요청에 이전 결과를 그대로 돌려주는 응답 캐시가 아닙니다. 사용자·목적지 해시, 전체 장소 ID, 핵심 명소 ID, 모델이 계획한 권역·경험 코드를 저장해 다음 코스의 반복을 줄입니다.

- 기본 보관: **최근 30일·사용자/목적지당 20개·전체 10,000개**.
- 전체 장소와 핵심 명소 중복률을 따로 계산합니다. 식당만 교체한 코스가 새 여행으로 평가되지 않도록 합니다.
- 중복률은 겹치는 ID 수를 두 코스 중 작은 집합 크기로 나누고, 이전 코스별 비교의 최댓값을 사용합니다. **40% 이하는 우선 선택 목표**이며 항상 거부하는 절대 조건은 아닙니다.
- 장소 수 충족을 먼저 평가하고 그 범위에서 다양성·권역 응집도·경험 반복을 비교합니다. 최종 저장은 SQLite 트랜잭션에서 최신 이력을 다시 검사합니다.
- 같은 DB를 공유하는 서버 범위에 적용됩니다. BE 저장 코스·다른 서버 이력을 자동 연동하지 않습니다. 이력 읽기·쓰기 장애에는 생성을 이어가되 반복 억제가 제한됨을 안내합니다.
- 일정 확정 때 저장하므로 이후 연결이 끊겨 사용자가 받지 못한 결과도 이력에 남을 수 있습니다.

### 현재 적용한 호출 절감

- 먼저 ID 검색을 하고 한 ID가 확인되면 상세를 조회합니다. 지점이 모호하거나 주변 후보 보충이 필요하면 상세 필드 검색을 사용합니다.
- **동일 생성 요청 안에서** 장소·경로 성공 응답과 검증 결과를 재사용하고 중복 조회를 공유합니다. 실패는 성공 캐시에 넣지 않고 다음 단계에서 일시 장애를 다시 확인할 수 있습니다.
- 완료 날짜는 다시 생성하지 않고 추가 명소·식당 검색 횟수와 후보 수를 제한합니다.
- 사진은 확정 장소만 조회하고 대표 이미지에 재사용합니다. 추천 이유·요약·이동 메모 작성만을 위한 추가 LLM·Maps 요청은 없습니다.
- 종료 시 `Maps request cost summary`에 SKU별 실제 HTTP 시도·성공·오류·캐시 적중과 코드에 등록된 단가 기준 USD 추정치를 기록합니다. 무료량·할인·환율·세금·LLM 토큰 비용은 포함하지 않으므로 실제 청구액과 구분합니다.
Places 상세·사진 응답을 SQLite 생성 이력에 장기 저장하지 않습니다. 주소·좌표·장소명·영업시간과 사진은 요청 간 캐싱 대상이 아니며, 이력에는 ID와 독립적인 계획 메타데이터만 보관합니다. 추가 보충·대안 경로·재시도에는 비용이 발생할 수 있어 이 개선만으로 코스당 청구 비용이 반드시 감소한다고 보지는 않습니다.

| 조합 선택 | 다양성 평가가 방문 수보다 우선 | 정상 하한 충족 → 다양성·권역 응집도 → 동등한 조건의 방문 수 |
| 최종 복구 | 바로 3곳 조합으로 축소 | 5곳 → 4곳 → 3곳, 각 4개·총 12개 경로 조합 한도 |

관광·체험 후보가 부족하면 해당 일자와 부족 수를 전달해 기존 생성 횟수 안에서 보충한다. 이미 정상 하한을 채운 다른 날짜는 유지한다. 보충 전에 검증된 작은 전체 코스를 보관하며, 새 후보 검증·모델 요청이 실패하거나 남은 시간이 부족하면 보관 코스를 반환한다.

**최종 자동 검증:** 새 방문 수 회귀 19개를 포함해 필수 `test.sh` **exit 0, Ruff 통과, 전체 562개 테스트 통과**. 모의 LLM·Maps와 실제 그래프·임시 SQLite로 검사했으며 실 유료 API 요청은 실행하지 않았다.

- 느긋함 5곳·기본 6곳·촘촘함 7곳의 후보가 충분할 때 구성과 관광·체험 3곳을 확인했다. 모든 성향에서 검증된 5곳이 있으면 목표 6~7곳만을 위한 추가 LLM 요청을 하지 않았다.
- 카페·음식점·조식이 관광 부족을 가리지 못하도록 검사했다. 부족 명소 1곳 보충에서는 기존 장소 재조회 없이 새 명소만 1회 조회했다.
- 2일 코스에서 정상 5곳인 첫날을 유지하고 부족한 둘째 날만 보충해 5곳·5곳으로 반환했다.
- 보충 timeout·잘못된 위치·시간 부족에도 검증된 4곳과 실제 수 안내를 반환했다. 이전 이력 없는 요청에 중복 안내를 붙이지 않았다.
- 5곳의 경로가 90분을 초과하는 상황에서 안전한 4곳을 3곳보다 먼저 반환했고, 정상 5곳 복구에는 축소 메모를 붙이지 않았다. 실제 대안이 3곳뿐인 경우에는 확인된 장소만 반환하고 수를 안내했다.
**범위:** 5곳은 정상 생성의 하한이다. 정해진 후보·횟수·시간·조합 범위에서 확보하지 못하면 검증된 축소 일정이 안전 예외로 반환될 수 있다. 모든 후보의 전역 탐색이나 항상 5곳 이상의 성공을 보장하지 않는다. 실제 서비스 방문 수 분포·반복률·성공률·완료 시간·비용 측정은 후속 과제다.
